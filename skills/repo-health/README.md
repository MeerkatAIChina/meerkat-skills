# Repo Health — 一条命令看懂你的仓库有多健康

> 不是只有 CI 红了你才应该看仓库。一个健康的仓库，是能安静地承受贡献者涌入、安全扫描和社区审视的。

## 痛点：假装很健康的仓库

你知道你的仓库有没有 SECURITY.md 吗？你的默认分支叫 `main` 还是 `master`？你的 `.env` 文件是不是被不小心提交到 Git 历史里了？有多少个分支三个月没动过？——这些问题，大多数团队不敢回答。

更危险的是：当你准备把一个私有仓库开源，你以为"加个 LICENSE 就够了"，实际上你还缺 CONTRIBUTING.md、Issue 模板、分支保护、Social Preview 图片……而对公开仓库来说，这些缺失就是信任流失。

## 能力：全维度打分 + 优先级修复

`repo-health` 是一次命令级的仓库体检。它从五个维度给你的仓库打分（0-100）：

| 维度 | 权重 | 关注什么 |
|------|------|---------|
| **标准文件** | 30% | LICENSE、README、.gitignore、SECURITY.md、CONTRIBUTING.md、CODEOWNERS 等 |
| **GitHub 配置** | 15% | 仓库描述、Topics、默认分支名、分支保护规则 |
| **文档质量** | 25% | README 完整度、CHANGELOG 是否存在和更新频率 |
| **代码卫生** | 20% | 过期分支、被跟踪的 .env 文件、大体积二进制文件 |
| **社区友好** | 10% | CODE_OF_CONDUCT、Issue/PR 模板 |

输出是完整的评分报告 + 按优先级排列的修复建议（HIGH / MEDIUM / LOW）。如果你加 `--fix` 参数，还能自动生成缺失的文件——但绝不覆盖已有内容，也绝不替你推送。

公开仓库会被更严格的标准审视，私有仓库则跳过部分社区相关检查。不做无意义的焦虑制造，必须项和加分项清楚区分。

## 谁在用？

- **团队 Lead / 架构师**：接手遗留仓库时快速摸底。
- **开源项目维护者**：发布前的标准化检查清单。
- **DevOps / SRE**：批量评估组织中多个仓库的健康基线。
- **独立开发者**：确保自己的开源仓库经得起社区审视。

## 配合其他技能

- **`repo-scaffold`**：`repo-health` 发现问题 → `repo-scaffold` 生成缺失文件。
- **`github-readme`**：文档维度的警告可以交给 `/github:readme audit` 深入分析。
- **`dep-audit`**：做完仓库结构体检后，再做依赖安全审计。
- **`safe-push`**：修复完成推送前，做最终安全扫描。

> **"一个健康的仓库不需要英雄来拯救——它用标准化文件、自动化检查和清晰规则保护自己。"**
