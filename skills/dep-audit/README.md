# 🔍 依赖审计引擎 — 别让一个过期的依赖炸掉你的营销技术栈

> **你网站上的那个三年前没更新的 npm 包，可能正在成为黑客的后门。而你还不知道。**

---

## 你正面临的痛点

营销团队管着越来越多的技术资产：Landing Page、数据分析 Dashboard、自动化脚本、WordPress 插件、Shopify App……每一个都依赖几十上百个第三方包。一个 CVE 漏洞爆出来的时候，你能不能在三分钟内知道自己的哪些项目受影响？还是等到安全团队发邮件你才慌？

更隐蔽的风险是**许可证合规**——你引了一个 GPL 包，你的商业项目可能面临开源义务。还有**版本漂移**——前端用 `react@18.2`、后端用 `react@17.0`，没人发现，直到线上炸了。

---

## 这个 Skill 能做什么

| ✅ 能做 | ❌ 不做 |
|---------|---------|
| 扫描 package.json / pyproject.toml / Cargo.toml / go.mod 等所有主流包管理器 | 不会自动升级任何依赖——决定权永远在你 |
| 标记过期依赖并分级（Patch 安全 / Minor 新功能 / Major 破坏性变更） | 不会修改你的代码 |
| 运行安全审计（npm audit / pip-audit / cargo audit / govulncheck） | 不会忽略锁文件——锁文件是真相的唯一来源 |
| 跨仓库版本对比——同一依赖在不同仓库的版本冲突一表打尽 | 不会用最新版本替换所有依赖（不是所有 outdated 都是 broken） |
| 许可证兼容性扫描——GPL/AGPL 在 MIT 项目中 = 红旗 | 不会替代你现有的 CI/CD 安全流水线 |

## 核心能力

| 能力 | 说明 |
|------|------|
| **多生态系统** | Node.js (npm/yarn/pnpm)、Python (pip/poetry/uv)、Rust (cargo)、Go (go mod) |
| **安全优先排序** | Critical → High → License 违规 → Major 过期 → 跨库冲突 → Minor/Patch 批量更新 |
| **跨仓库分析** | 多个仓库之间同一依赖的版本漂移检测 + 推荐统一目标版本 |
| **许可证审计** | 检测 Copyleft 污染、未知许可证、许可证冲突、非 OSI 许可 |
| **分批更新策略** | 识别可一起更新的依赖组（如同组织包 `@babel/*`、peer dependency 链） |

### 八步审计流程
1. **检测包管理器** — 找到所有 manifest 和 lock 文件
2. **解析依赖** — 区分生产依赖和开发依赖
3. **过期检查** — 查询注册表最新版本，按影响分级
4. **安全扫描** — 运行生态原生审计工具
5. **跨仓库分析** — 多仓库版本冲突对比
6. **许可证扫描** — 合规性检查
7. **更新计划** — 按优先级排序的行动清单
8. **生成报告** — 严重编码表格 + 统计总结

## 谁应该用

- ✅ 营销技术团队负责人——你管着 3+ 个营销网站/工具，需要统一的依赖健康视图
- ✅ 开源项目营销负责人——开源前的最后一道安全闸门
- ✅ CTO/技术创始人——发布前确认没有高危漏洞
- ✅ 市场运营团队——你维护的落地页代码库也需要定期安全检查
- ✅ 咨询顾问——接手的客户项目先做一次依赖健康度基线
