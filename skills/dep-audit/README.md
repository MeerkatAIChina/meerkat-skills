# Dependency Audit — 你的依赖树不是一棵树，是一张不断蔓延的风险网

> 每次 `npm install` 你带回家的不只是功能代码，还有 CVE、许可冲突和跨仓库版本分裂。等你发现了，通常已经晚了。

## 痛点：依赖管理是"眼不见为净"的重灾区

大多数项目的依赖管理处于三种状态之一：

1. **不知情** — `package.json` 里写着 `^2.3.1`，实际装了什么版本？锁文件里可能有 47 个间接依赖带着已知漏洞。
2. **不敢动** — 知道某个依赖严重过时（major 版本跳了 3 个大版本），但怕升级引发连锁 break，于是一直拖着。
3. **不一致** — 三个仓库共用了同一个包，但分别锁在 1.x、2.x 和 3.x 版本上。版本分裂意味着三个仓库暴露在不同的漏洞面上，修复成本乘三。

再加上许可证问题——你在 MIT 许可的项目里悄悄引了一个 GPL 依赖——当你准备开源或接受审计时，这就是一颗定时炸弹。

## 能力：全生态依赖审计 + 跨仓库版本横评

`dep-audit` 覆盖四大主流生态（Node.js / Python / Rust / Go），对单个或多个仓库执行深度依赖审计：

- **过期检测** — 区分 Patch（Bug 修复，可批处理）、Minor（新特性，应向后兼容）和 Major（破坏性更新，需迁移评估），不制造"最新恐惧症"。
- **安全漏洞扫描** — 调用各生态原生工具（`npm audit`、`pip-audit`、`cargo audit`、`govulncheck`），按 Critical / High / Medium / Low 分级。
- **跨仓库版本冲突分析** — 当你审计多个仓库时，自动对比共享依赖的版本差异，给出推荐对齐版本。
- **许可证合规扫描** — 检查是否有 GPL/AGPL 依赖混入 MIT/Apache 项目，标记未知许可和无许可的依赖。

最终输出是一张**按优先级排好序的更新计划表**：Critical 安全漏洞永远排第一，跨仓库版本分裂次之，Minor/Patch 批处理收尾。同一个组织的包（如所有 `@babel/*`）、peer dependency 链条会被自动归组，避免拆开更新导致版本错配。

**绝不自动更新。** `dep-audit` 只审计和建议。升级的时机和范围由你决定。

## 谁在用？

- **全栈 / 平台工程师**：日常维护中的依赖健康检查。
- **安全工程师**：CVE 爆发时快速评估受影响范围。
- **技术负责人**：接手新仓库时建立依赖基线。
- **开源维护者**：许可证合规审计（"我们真的可以开源吗？"）。

## 配合其他技能

- **`repo-health`**：仓库结构体检 + 依赖安全审计 = 完整的仓库健康画像。
- **`sync-repos`**：公开仓库同步后运行依赖审计，确保发布侧无已知漏洞。
- **`release-notes`**：发布前确认本次更新不引入新的安全风险。

> **"'能跑就行'的依赖管理，最后都会变成'不跑也行'的生产事故。"**
