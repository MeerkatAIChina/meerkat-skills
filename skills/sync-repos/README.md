# Sync Repos — 你的私有开发仓库和公开仓库之间，再也不会有"同步漏了"

> 当你同时维护一个私有 dev 仓库和一个公开 release 仓库时，每一次手动复制文件都是在赌博——赌的是你没有把内部文档、测试数据和开发密钥一起拷过去。

## 痛点：公私仓库双轨制的同步噩梦

越来越多团队采用"私有开发 + 公开发布"的双仓库策略。开发在私有侧尽情迭代，发布前把干净内容同步到公开侧。听起来理想，执行起来充满危险：

- 配置文件（`.env`、内部规划文档、客户相关代码）被误同步到公开仓库——你可能几周后才有人来提醒。
- 公开仓库的 README、CONTRIBUTING.md、GitHub Actions 工作流是单独维护的——一次粗心的全覆盖同步可能把它们全抹掉。
- 两边不同步了几周？哪些文件在私有侧改了但没过去？没有人真的会手动比对文件列表。

## 能力：检查 + 同步 + 安全验证的三段式工作流

`sync-repos` 为公私仓库对提供完整的生命周期管理：

- **`check` 模式** — 对比两侧文件差异，按"预期排除 / 意外漂移 / 内容分歧 / 公开独有"分类报告。告诉你从上次同步至今落后了多少个 commit。
- **`sync` 模式** — 先执行 check，确认有漂移后运行同步脚本，同步完成后自动对公开仓库做 PII/密钥扫描。发现问题立即阻断。
- **`setup` 模式** — 分析你的私有仓库结构，自动生成 `sync-public.conf`（排除规则配置）和 `sync-public.sh`（rsync 同步脚本）。识别哪些文件永远不该出现在公开侧。

核心安全策略：**排除列表只增不减，公开独有文件永不被覆盖，每次同步后强制扫描。** 同步只是写入了本地文件——推送由你通过 `safe-push` 单独确认。

## 谁在用？

- **开源项目维护者**：管理 dev mirror → public release 的同步管线。
- **SaaS / DevTools 团队**：核心引擎私有开发，示例和 SDK 公开。
- **安全敏感团队**：对内代码和对外代码必须物理隔离的合规场景。
- **独立开发者**：维护个人品牌开源项目，同时保留 experimental 分支的隐私。

## 配合其他技能

- **`safe-push`**：同步完成后推送公开仓库前的安全扫描（天然衔接）。
- **`repo-scaffold`**：脚手架的排除标记文件（`.syncignore` 等）直接对接同步配置。
- **`dep-audit`**：同步后对公开仓库做依赖安全审计。

> **"同步不是复制粘贴。同步是一套规则、一个脚本、一次验证——把'我不会搞砸'变成'我没法搞砸'。"**
